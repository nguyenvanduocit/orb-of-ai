# discord-claude-bot

"Orb Of AI" — Discord bot on **discord.js v14** (gateway) + **@anthropic-ai/claude-agent-sdk**. Runtime: **Bun** (never npm/node). ESM, strict TypeScript, local imports WITHOUT extension (`import { config } from "./config"`).

Two lanes (both server-only — every slash command & context menu is declared guild-only at registration (`contexts: [Guild]` in `commandData`) so Discord hides them from DMs; the DM message intent is off, so a DM to the bot never reaches an agent lane):
1. **Agentic chat** — @mention the bot or reply to it in a server → Claude Agent SDK answers (one-shot `query` with session resume per channel; cwd = the server's own workspace). The agent is self-aware of the bot: `buildContextAppend` (src/agent.ts) injects a capabilities section built from the live registry (`commandCatalog()` in `src/commands/index.ts`, the same source `/help` renders — never drifts) so it can explain features and point users at the exact command. Every run also gets a sender-bound in-process `bot` MCP server (`src/agent-tools.ts`, attached in chat.ts and hoi.ts alongside `poe`) whose tools wrap the same exported rule cores as the slash commands (`performCheckin`/`attendanceRanking` in diemdanh.ts, `transfer`/`coinRanking` in coin.ts, `buyTitle`/`equipTitle`/`unequipTitle`/`titlesShop`/`memberTitles` in danhhieu.ts, `buyLottery`/`lotteryInfo`/`lotteryHistory` in xoso.ts, and — season-gated on `FOOTBALL_DATA_TOKEN` — `placeBet`/`cancelBet` in worldcup.ts) — so "nhờ bot điểm danh / chuyển coin / mua & đeo danh hiệu / giành số xổ số / đặt & hủy kèo World Cup" all work agentically without a slash command. Features with no tool (interactive games /baucua /masoi /noitu /blackjack /poker /roulette /duathu /oantuti, the /poe panel, /coindrop, /clear) are routed to their command. A new bot_* tool is registered nowhere else: the SDK advertises each tool by its own description and the prompt's Bot Actions section is policy-only (no tool names). Abuse guards: every tool acts on the sender only, and `bot_coin_transfer` mechanically refuses unless the recipient's mention/ID appears in the sender's OWN current-message text (`senderText` — quotes excluded, `""` for the "Hỏi AI" menu), so instructions smuggled through quoted messages or earlier session turns can never name a beneficiary. The Protected Files rule in the append still bans touching the ledger files directly; the mcp__bot__ tools are the only sanctioned mutation path.
2. **Programmatic slash commands** — pure TypeScript, no AI: `/ping`, `/help` (hướng dẫn — ephemeral embed, danh sách lệnh build động từ registry nên không bao giờ lệch), `/diemdanh` (checkin|bxh|stats), `/coin` (sodu|bxh|tang|doino|anxin), `/coindrop` (admin thả coin cho cả kênh nhặt — see Coin drop), `/baucua`, `/noitu` (sòng nối từ — lobby + stake buttons, see Games), `/masoi` (Ma Sói — social-deduction trong chat của kênh voice, see Games), `/oantuti`, `/duathu` (đua thú — see Games), `/blackjack` (bàn xì dách nhiều người, chủ bàn làm nhà cái — see Games), `/poker` (Texas Hold'em No-Limit 2–8 người, peer-pot không nhà cái — see Games), `/roulette` (vòng quay roulette châu Âu, chủ ván làm nhà cái — see Games), `/xoso` (mua|thongtin|lichsu|kenh) and `/danhhieu` (shop|mua|deo|thao|xem) — the two coin sinks, see Coin sinks, `/hoi`, `/clear`, `/poe` (a single settings-panel command, no subcommands — connect / pick default character / disconnect are buttons + a select menu inside an ephemeral dashboard), `/flex` (bxh|nhanvat — public PoE wealth leaderboard + character card, see Path of Exile), `/bug` (baocao|list|xem — báo lỗi của bot cho dev, see Bug reports), `/worldcup` (list|cuoc|ve|huy|kenh — seasonal, see World Cup betting). Coin also has two user context menus: right-click a member → Apps → "Chuyển coin" (modal asks the amount) or "Đòi nợ" (modal asks amount + reason, posts the same request as the slash subcommand) — `contextMenus`/`handleContextMenu`/`handleModal` on the coin command. `/coin doino` (đòi nợ) pings a specific target with Đồng ý/Từ chối buttons; accepting runs the balance-checked transfer target → requester (request state lives entirely in the button customId — stateless, survives restarts; a module-level settled-set blocks double-accept — copy in the `DOINO` table in coin.ts). `/coin anxin` (ăn xin) is a **separate, non-targeted goal-based beg** — deliberately not the đòi nợ path, so the two never conflict: the beggar sets a coin mốc (`/coin anxin soluong:<goal> [lydo]`) and posts a public card with a progress bar; anyone but the beggar can give — a **Cho 10 🪙** quick button + a **Cho tuỳ tâm 💰** modal for a custom amount, each gift capped at the remaining and transferred giver → beggar immediately (no escrow) — and it **locks when collected ≥ goal**. The beggar can **Đóng nón** to end early; an unfilled beg auto-closes at a 1-hour deadline (gifts are final — nothing to refund). One open beg per channel, state in `begs.json` keyed by channel (synchronous load→mutate→save so concurrent givers can't race, restart-safe via persisted deadline + `startBegScheduler`, the pure-ish `giveToBeg` conserves coins). Since it no longer names a person, ăn xin has no context menu. Top-level shortcuts `/anxin`, `/doino`, `/tang`, `/sodu`, `/checkin` (`src/commands/shortcuts.ts`) alias those subcommands: `data` is the subcommand's own JSON lifted from the parent builder (never drifts), execute forwards through the optional `sub` param on `Command.execute`. Hoi also has one message context menu: right-click a message → Apps → "Hỏi AI" sends that message's text AND any image attachments to the agent (same channel session and speaker format as `/hoi`; the quoted-message framing and the download-to-`tmp/` image path both mirror chat.ts, so the agent Reads the images and an image-only message is answerable) — `contextMenus`/`handleMessageContextMenu` on the hoi command; only a message with neither text nor a readable image gets an ephemeral refusal. Since users split one thought across several quick messages, the quote covers the whole consecutive same-author burst around the clicked message (`collectBurst` in hoi.ts, pure/exported: ≤5-min gaps, any other author breaks the run, scanned both directions, joined text capped at 2000 chars); the neighbor fetch is best-effort — on failure only the clicked message is quoted (and only its own images collected). Images ride the same burst, capped at 4 like chat.ts, through the shared `collectImageCandidates`/`downloadImages` in agent.ts — both agent lanes' one image path (download to `<workspace>/tmp/`, list paths for the Read tool, delete after the run).

## Data: one shared world, many rooms

Storage splits on a single question — **"who is this player?" is global, "what is happening in this room?" is per-guild** (`src/store.ts` owns both roots + the atomic-write/quarantine convention, and is imported by every store layer so there is no evaluation cycle).

**`data/global/` — the shared world (`src/economy.ts`, `src/rpg-store.ts`).** One wallet, one check-in streak, one title collection, one hero per PERSON, across every server the bot is in: `coins.json`, `attendance.json`, `titles.json`, `lottery.json` (one jackpot for everyone), `betting.json` (one pari-mutuel book per match), `settings.json` (weekend x2 + the Tier-2 event + the RPG season), `characters.json`, `expeditions.json`, `expedition-results.json`, `market.json`, `pvp.json`. A player earns in one server and spends in another; joining a second server costs them nothing to re-grind. **The faucets are global for a mechanical reason, not a stylistic one:** the moment coins are shared, a per-server faucet is a money printer — check-in stored per guild would pay the same person once per server per day, a per-server event multiplier would be an arbitrage anyone can shop for, and `STARTING_COINS` would mint once per server. Check-in is therefore once per day system-wide, the starting wallet once per lifetime, and the event multiplier system-wide.

**`data/guild_<guildId>/` — one room (`src/guilds.ts`),** provisioned by copying `template/` on install. It holds `CLAUDE.md` (personality), `data/` (agent memory), `sessions.json` (channel → Claude session id), `settings.json` (announce channel, onboarding, weekend-announce dedup), `streams.json` (in-progress voice reward sessions — a voice session IS a room, and one person can only sit in one at a time, so there is nothing to farm across servers), `drops.json`, `begs.json`, and `games/` (one live table per channel). The `data/dm_<userId>/` naming is reserved for future per-user DM support.

Lifecycle (`src/guilds.ts` + events in `src/index.ts`):

- Startup → `migrateToGlobal()` folds any surviving per-server ledgers into `data/global/` (see Migration), then `rollRpgSeason()` runs ONCE for the whole system — one league, one reset, so two servers can never sit on different seasons of the same shared characters
- Install / startup → `syncGuild`: provision workspace (+ `refreshSkills` overlays `template/.claude/skills` every sync, so a new/updated skill reaches servers provisioned earlier — the one-time template copy never would; only `.claude/skills` is touched, personality/`data/` untouched) + grant `STARTING_COINS` (default 100) to every human member who has no wallet yet. It **prunes nobody** — that was right when each server had its own economy, and is now the one thing that must never happen on a leave
- Member joins → a starting wallet only if they've never had one; member leaves → only their in-progress voice session in THAT server (`removeGuildMemberState`), then `forgetIfGone` checks whether they still share any server with the bot and deletes their wallet/hero only if they don't
- Server removes the app (GuildDelete) → that `data/guild_<guildId>/` folder is deleted; its members keep everything, since most are probably playing elsewhere
- GC for the shared stores → `sweepOrphans` (startup after every sync, then every 6h, plus on GuildDelete): forgets anyone holding global state who is in no server with the bot. **It deletes nothing unless EVERY guild's member list was fetched in full** — a partial fetch looks exactly like "everybody left", and this function's whole job is deleting wallets
- `/diemdanh checkin` rewards coins on a repeating streak cycle (`CHECKIN_SCHEDULE` in diemdanh.ts, default `[100, 250, 500, 800, 1200, 2000, 5000]`): the reward for a check-in is `CHECKIN_SCHEDULE[(streak−1) % CYCLE_LEN]`, so it escalates across the week, day `CYCLE_LEN` is the jackpot, then it loops; a missed day resets the streak (and thus the reward) to day 1. No new stored state — the tier is derived from the existing `attendance.json` dates via `currentStreak`. Every check-in (and `/diemdanh stats`) renders the cycle ladder (`renderRoadmap`, pure/exported) showing claimed/today/upcoming/jackpot days
- Time in a voice channel earns coins on **two tiers** (`src/streams.ts`), so a weak machine that can't stream still cày coin by hanging out: **Go Live** pays `STREAM_COINS_PER_BLOCK` (default 10) per `STREAM_BLOCK_MINUTES` (default 5) block regardless of audience, while **just sitting in voice** pays the much lower `VOICE_COINS_PER_BLOCK` (default 2) per block — but only when the channel has **≥2 humans and isn't the AFK channel** (no solo 24/7 farming; a member alone or in AFK burns the block without pay). **One session per member exists WHILE THEY'RE IN VOICE** (opened on join, not on Go Live), keyed by userId in `streams.json`. A once-a-minute `streams` ticker (`startStreamScheduler`, `startTicker` + `forEachGuild`, started unconditionally in `src/index.ts`) credits each newly-completed block at whichever tier is live **at payout time** (`tierFor`) and keeps **one live message** in the voice channel's text chat — first paid block posts it, later blocks edit it, the leave finalizes it into a summary (`settleSession` pays the last unpaid block at the tier the ticker last recorded on the session's `rate`). **No double count by construction:** the single monotonic `paidBlocks` counter means a block is paid exactly once — the tier only changes coins-per-block, never *which* block is paid, so a streaming member is never counted by both tiers. Sessions open/close on voice **join/leave** edges (`handleVoiceStateUpdate`); a channel switch keeps the clock (message stays put, eligibility follows the member's live channel). Restart-safe: `streams.json` persists `paidBlocks`/`paidReward`/`rate`/`messageId` (each block is marked consumed **before** crediting, so a crash under-pays rather than double-pays), and reconcile on startup settles members no longer in voice while the ticker resumes those still connected. Needs the non-privileged `GuildVoiceStates` intent

Requires the **Server Members Intent** (privileged) enabled in the Discord Developer Portal — login fails with "Used disallowed intents" without it.

## Path of Exile (`src/poe.ts`)

OAuth is the single mechanism and covers **both games** — one connection, since `account:characters` spans PoE1 (`pc` realm) and PoE2 (`poe2`). Two client modes, chosen at runtime by `oauthClient()`:

**Public (default, no GGG registration)** — `client_id=pob`, Path of Building's own public PKCE client that GGG pre-registered with loopback redirects. Zero setup, works out of the box. The loopback (`http://localhost:49082`) lands on the *user's* machine, so the panel's **Kết nối** button shows a Link button + a **"Dán code"** button: the user authorizes, copies the `?code=...` from their address bar, pastes it into the `poe:code:<state>` modal, and the bot exchanges it (`extractCode` accepts the raw code or the whole pasted URL). Requests send **no client_secret** and mirror PoB's `User-Agent` — traffic rides PoB's client identity, so keep requests single + rate-limited, **never add auto-retry loops**.

**Confidential (upgrade)** — set `POE_CLIENT_ID`/`POE_CLIENT_SECRET`/`POE_REDIRECT_URI` (registered via oauth@grindinggear.com, HTTPS redirect on the registered domain) and `oauthClient()` switches to a clean web callback served in `src/server.ts` (client_secret sent, own UA). `poeConfidential()` / `poeCallbackPath()` gate this; the panel's Kết nối button then uses a plain Link button (no paste step).

- **Both games from one link:** `fetchCharactersFor` merges `GET /character` (PoE1 PC) + `GET /character/poe2` (PoE2, best-effort so a PoE1-only account still lists); `fetchCharacterFor(userId, name?)` resolves the realm into `/character/<realm>/<name>` — with `name` omitted it uses the stored **default character** (realm carried, so no list call). `/poe characters` tags PoE2 entries. Tokens refresh lazily, single-flight per user; a 401 that survives one forced refresh unlinks.
- **`/poe` is a single ephemeral settings panel** (`connectedPanel` in `src/commands/poe.ts`) — rich account embed (account, realm, guild, twitch, character count, top 10 chars, default char, connect time, token expiry) + a character **select menu** to set the default inline + Làm mới / Ngắt kết nối buttons; when disconnected it shows a Kết nối button. All state transitions happen on the one message (button → `handleButton`, select → `handleSelect`, paste-code modal → `handleModal`); no subcommands.
- **Default character** (`account.defaultCharacter = {name, realm}`): set via the panel's select (`poe:default` → `setDefaultCharacter`); preserved across a reconnect of the same account, wiped on account change. It's what build/wealth features default to when the user names none — the `poe_character` agent tool takes an optional name and falls back to it. (Wealth/stash will additionally need the `account:stashes` scope, which the public `pob` client may not carry — revisit when building stash.)
- **Token store** `data/poe-accounts.json`, user-scoped (survives guild wipes), AES-256-GCM, key = HKDF(`DISCORD_BOT_TOKEN`) — not in the chat agent's whitelisted env (`AGENT_ENV` in `src/agent.ts`, never spread `process.env` there), so the agent reads the blob but can't decrypt it.
- Agent chat gets an in-process MCP server per message (`buildPoeMcpServer(senderId, workspace)` via `runAgent({ mcpServers })`), sender-bound, attached only when `hasPoeConnection(senderId)`; no token crosses the tool boundary. Tools: `poe_profile`, `poe_characters`, `poe_character` (slimmed gear + gem/skill setup → qualitative build analysis), `poe_export_character` (writes the FULL char JSON to `<workspace>/data/character-exports/oauth-<name>.json` in the `pob` skill's format → the agent runs the workspace `/pob` skill's export-pob/calc on it for exact stats: DPS, EHP, resistances, keystones), and `poe_wealth` (estimates "độ giàu"). Build analysis adds no extra GGG calls beyond the one character fetch — PoB calc is local.
- **Wealth estimate** (`estimateWealth`): prices the character's equipped **uniques** via poe2scout's public API (`api.poe2scout.com`, no-auth, covers both realms; prices in Exalted, `DivinePrice` converts to Divine). The unique catalog per (realm, league) is cached in-memory 30 min (`catalogCache`) to respect poe2scout's rate limit. It is a **FLOOR, not net worth** — rares (priced by mod-roll, not a catalog) and the currency stash (needs `account:stashes`, which the public `pob` client lacks) are excluded; the tool + its result say so and the agent must present it that way.
- **Wealth nickname** (`reflectWealthNickname`): every `poe_wealth` run also best-effort re-suffixes the sender's server nickname with ` ⚜~N div` (old suffix stripped, base name truncated to fit Discord's 32 chars). Needs the **Manage Nicknames** permission + bot role above the member; the server owner can never be renamed (Discord rule) — skips are silent, the status lands in the tool result's `nickname` field for the agent to relay. Update is strictly lazy (only when the user themselves triggers a wealth fetch) — no scheduler, so it adds zero GGG API traffic. `buildPoeMcpServer` takes the sender's `GuildMember` as an optional third arg for this; without it the nickname step is skipped.
- **Ban-risk (accepted, mitigated):** the OAuth character API is the flagged path per the workspace `pob` skill; keep calls single + rate-limited, surface Retry-After, no retry loops. GGG rate limits are dynamic.
- **`/flex` (`src/commands/flex.ts`)** — public khoe: `bxh` ranks `listPoeConnections()` ∩ guild members by `estimateWealth` (SEQUENTIAL calls behind a module-level 30-min cache, capped at 15 users — rate-limit courtesy), `nhanvat` renders a character card (level/class/league + top priced uniques). Every wealth number carries the floor caveat: uniques-only, not net worth.

## Games

One active game per channel, persisted at `data/guild_<guildId>/games/<channelId>.json` (`loadGame`/`saveGame`/`endGame` in `src/guilds.ts`) — state survives restarts and dies with the server folder. Each game is one command file: a pure reducer core (exported, testable) + Discord glue; the two betting-board games (bầu cua, đua thú) share ALL their glue through `boardGameCommand` in `src/games.ts` and keep only catalog + copy + `decide`/`present` in their files.

- Buttons, string select menus and modal submits route by customId `"<commandName>:..."` → `Command.handleButton` / `Command.handleSelect` / `Command.handleModal`; context menus route by the menu's own name via `contextMenuCommands` → `Command.handleContextMenu` (user) / `Command.handleMessageContextMenu` (message) (all dispatched in `src/index.ts`)
- Timed phases persist a `deadline` timestamp; the in-memory timer (`scheduleDeadline` in `src/scheduler.ts`) is best-effort and the next interaction resolves the round lazily after a restart
- One global sweeper (`sweepIdleGames` in `src/index.ts`, every 5 min + once at startup, via `startTicker`) cleans up any game idle > 20 min via the command's optional `handleExpiredGame` (bầu cua refunds all bets, nối từ posts the summary) or deletes the file; `saveGame` stamps `updatedAt` to measure idleness. If teardown throws, the file is parked as `.failed-<timestamp>` (`quarantineGame`) — it may be the only record of players' stakes
- Coin moves are synchronous load→mutate→save (no await in between) so they're atomic on the event loop
- `/baucua` — betting round via symbol buttons (10 🪙/click), host rolls early or auto-roll at deadline, then a "xóc đĩa" reveal animation (`playAnimation` in baucua.ts): a covered bowl rattles 3 frames, the dish lifts and each hột flips up one at a time, then the settle embed — coins are settled BEFORE the theater (same invariant as đua thú), a crash mid-animation loses nothing. **The host is the house** (`hostIsBanker: true`): losing stakes flow to the host and winning payouts come out of the host's own balance, so coins circulate instead of being minted/burned (the fixed-odds edge lands on the host, not the void). The host may not bet, and every bet is gated up front against `baucuaMaxLiability` (the priciest of the 216 dice rolls given the current per-symbol stakes) so a bet the host couldn't cover is refused with a notice — the house is always solvent at lock. If the host's balance still drops mid-round, settlement caps as a backstop: the whole pool (stakes + host balance) is split pro-rata by entitlement, the host empties to 0 and keeps the rounding dust. The banker math is `bankerSettle` in games.ts (pure/exported, `Σ paid + hostDelta == totalStake` — coins conserved), applied by `settleBankerPayout` (drops ghosts + the host, one synchronous load→mutate→save). `settleBankerPayout` also burns a **`HOST_RAKE` (10%) fee on the host's net winnings** — the one deliberate burn (bettors pay no fee), charged only when the host profits (a losing or capped-out host pays nothing), taken AFTER settlement so it never touches the up-front solvency gate; the result embeds show it as a "🔥 Phí nhà cái" line. This is the whole answer to where each game's fee lands: the four player-hosted banker games (bầu cua, đua thú, blackjack, roulette) rake the host here in one place, while `/oantuti` (1:1 with the bot) and `/noitu` (peer pot, no banker) both charge no fee. The board shows the host's live quỹ and the result embed shows the house's P/L + a cap warning
- `/noitu` — word chain, zero-sum: a lobby message with Tham gia (stake 20 🪙 into the pot) / Bắt đầu / Huỷ sòng buttons; once playing, staked players chain plain 2-syllable words by typing in the channel (hooked in `src/chat.ts` before the mention filter), feedback via reactions ✅/❌/♻️/🚫. Host ends via Kết thúc (or the idle sweeper): the pot splits proportional to words chained (`settlePot`, pure/exported — remainder to the top scorer); nobody scored → stakes refunded
- `/oantuti` — ephemeral 30s button game, NOT persisted (a restart forfeits the stake): 10 🪙 deducted up front, win pays back **20** (`WIN_MULTIPLIER` 2×, net +10), draw/timeout refunds 10; it's **1:1 with the bot so no house fee** — a fair coin-flip (EV = 0). Because the bot isn't a real wallet, a win pays out of the void and a loss burns into it, so the game is net-neutral in expectation (neither a faucet nor a sink). On a pick the coins pay out first, then an "oẳn... tù... tì!" beat animation (the bot's hand shuffles ✊🖐️✌️ across 3 chants before both hands are revealed)
- `/duathu` — animal race: same `boardGameCommand` engine as bầu cua (6 animal buttons, 10 🪙/click, host runs early or auto-run at deadline) and the same **host-as-banker** model (`hostIsBanker: true`). Settlement is fixed-odds (`settleRace` + `simulateRace`, both pure/exported): backing the winner pays `PAYOUT_MULTIPLIER`× (5×, ~16.7% house edge over 6 runners), every other stake loses; the host collects the losing stakes and funds the wins from its own balance (`bankerSettle`, capped pro-rata as a backstop) — nobody backing the winner just means the house sweeps the board. Bets are gated up front against `raceMaxLiability` (5× the most-backed animal) so the house is never accepted into an outcome it can't pay. Coins are settled synchronously BEFORE the ~9-frame (18 max) 1.5s/frame track animation — the animation is pure theater, a crash mid-race loses nothing
- `/blackjack` — multiplayer xì dách, **host-as-banker** but NOT a board game: it has its own lobby→playing→dealer state machine in `src/commands/blackjack.ts`, reusing only the exported `bankerSettle` / `settleBankerPayout` from games.ts (the one home for the banker ledger math). One player opens a table as the dealer/bank; others buy in through a modal (variable stake, min **10** 🪙, ≤ **7** seats, host can't play their own table). `deal` shuffles a fresh **4-deck shoe per round** (independent each round → no card counting) and deals 2 cards each + 2 to the dealer (one hole card). Play is **turn-based**: seats act one at a time in join order, and the current turn is derived — not stored — as the first seat in `order` still status `playing` (`currentTurn`), since a hand leaves `playing` exactly when its turn ends (dừng/quắc/blackjack/gấp đôi). Only the turn-holder's Rút thêm / Dừng / Gấp đôi button is accepted (`state.seats[userId]` must equal `currentTurn`); anyone else gets an ephemeral "chưa tới lượt, đang chờ @X". A seat auto-stands on 21, busts >21, and Gấp đôi (only on the opening 2 cards) deducts a second buy-in, draws exactly one card, then ends the turn. Each turn has its **own 60s deadline** (`TURN_MS`): when it lapses, `expireTurn` stands the AFK turn-holder and advances (the in-memory `scheduleTurnTimeout` fires it; any post-restart click also self-heals via the same `Date.now() > state.deadline` path) — so one AFK player never blocks the table. Bots play their whole hand instantly at deal (`playBots`, thuần toán), so their already-settled seats are simply skipped by `currentTurn` and turns only stop on humans. When no seat is left playing (`currentTurn == null`) — or the idle sweeper fires — the dealer reveals its hole card and draws to 17 (stands on all 17, incl. soft 17), then `resolveTable` settles everyone: pure `settleHand` (natural blackjack pays **3:2** floored, win 1:1, push refunds, player bust always loses even vs a dealer bust) → `settleBankerPayout`. The board is a **Components V2** message (`ContainerBuilder` + `TextDisplayBuilder`/`SeparatorBuilder`, `MessageFlags.IsComponentsV2`) for its whole lifecycle — because Discord forbids editing a classic message into V2 (and back), every board render (lobby → playing → summary + animation frames + status/cancel) goes through `boardPayload`, which also sets `allowedMentions: { parse: [] }` so the many `<@id>` mentions render as names but never ping (V2 TextDisplay mentions notify by default, unlike embeds). The buttons live **inside** the container, and a `👉 Hành động dành cho @X — chỉ @X bấm được` line sits directly above the button row (the whole point of V2 here); the board also shows whose turn it is (`👉`), waiting seats (`⬜`), the dealer's up-card value, and a rules line. A **Luật** button opens the full rules as a classic ephemeral embed (separate message, not the board, so it stays non-V2 and works even after the table ends). Coin moves are synchronous (buy-in/double deduct on the event loop; settle runs BEFORE the dealer-reveal animation) so a crash mid-theater loses nothing — same invariant as bầu cua. Host solvency is gated at each buy-in: host quỹ must be **≥ 2× total buy-ins** (covers everyone doubling AND winning), so the house is always solvent at lock and bankerSettle's pro-rata capping is only a mid-round-drop backstop. The result embed shows the house's P/L + a cap warning and carries a **Ván mới** button (the clicker becomes the next host) for the play-again loop. The pure core (`freshShoe`/`handValue`/`isBlackjack`/`settleHand`) is exported/testable. **Cards render as custom application emojis** (`src/cards.ts` — the deck primitives `RANKS`/`SUITS`/`Card` live here now, shared with the asset pipeline): 52 card faces + a back, uploaded once via `bun run emojis:upload` (see Operations), fetched by name on ClientReady (`initCardEmojis`), with a plain-text fallback per card so a missing/not-yet-loaded emoji never breaks the board
- `/poker` — Texas Hold'em (No-Limit), the one **peer-pot card game with private hands** and NO banker: 2–8 người, its own `lobby → preflop → flop → turn → river → showdown` state machine in `src/commands/poker.ts` over a pure engine in `src/poker.ts` (reusing only `cardEmoji` from cards.ts + `againRow`/`fetchBoardMessage` from games.ts). Each player buys **variable chip stacks** from their coins (min **50**, blinds **5/10**) — different stacks make **side pots** real. Betting is **turn-based on ONE repainting board**: the turn line names who's up and the action row belongs to them (others bấm bị chặn — `/blackjack`'s pattern), buttons are **Bỏ bài / Bỏ qua(check) / Theo N / Tố ½ / Tố pot / 🔥 Tất tay** (No-Limit preset raises, labels carry the coin cost). Hole cards are private via a **👁️ Bài của tôi** ephemeral (shows the 2 lá + current best-hand hint from the flop on — `/masoi`'s ephemeral pattern), plus a **📋 Luật** ephemeral for beginners. Each turn has a **60s** deadline (`autoAct` = bỏ qua if free else bỏ bài; restart-safe three layers deep like the board games: persisted deadline → lazy resolve on next click → idle sweeper **VOIDs** the hand and refunds every buy-in). **Coin: peer-pot zero-sum like /masoi, /noitu** — coins become chips at buy-in, chips only move stack↔pot, every seat's final stack (+ pot winnings) is credited back, so **Σ credited == Σ buy-ins** (no banker, no rake, no mint/burn). Settle runs synchronously BEFORE any render — crash mid-hand loses nothing. **No AI bots** (poker needs human opponents). Pure core `best7`/`compareScores`/`handName`/`buildSidePots`/`awardPots`/`startHand`/`legalMoves`/`betPresets`/`act` exported and covered by `src/poker.test.ts` (`bun test`) — hand ranking, side pots, coin conservation
- `/roulette` — vòng quay roulette châu Âu (một số **0 xanh** + 1–36 đỏ/đen), **host-as-banker** and NOT a board game: its own betting-board flow in `src/commands/roulette.ts`, reusing only `settleBankerPayout` / `fetchBoardMessage` / `BET_STEP` from games.ts (the boardGameCommand engine can't host the modal roulette needs). One player opens a round as the house; others place bets until the host **Quay!** early or the **60s** deadline auto-spins (`scheduleAutoResolve`), then a decelerating wheel animation lands on the number. Bet surface splits by input: the **12 outside bets** (Đỏ/Đen, Chẵn/Lẻ, 1–18/19–36, 3 tá, 3 cột) are buttons at **10** 🪙/click; **straight numbers 0–36** go through a modal (`roulette:number`, variable stake ≥ 10 🪙) because 37 numbers can't be buttons. Payouts are the UnbelievaBoat table (total return): even-money bets **2×**, dozens/columns **3×**, straight **36×**. The **house edge is the green 0** — every outside bet loses on 0, only straight-0 wins, so all bets carry an identical **1/37 ≈ 2.70%** edge (verified). Pure core `settleRoulette` (bets + spun number → per-player credit/net) and `rouletteMaxLiability` (exact worst-case house payout: try all 37 outcomes against the aggregate book, take the max) are exported. Solvency is gated on **every** bet (button and modal, via one shared `solvencyRefusal`): a bet is refused if the priciest of the 37 outcomes would exceed pot + host balance — so a lone 10 🪙 straight needs the house to cover 360, and the house is always solvent at lock; `bankerSettle`'s pro-rata capping is only a mid-round-drop backstop. Coins settle synchronously (deduct on click/submit; spin settles BEFORE the animation) so a crash mid-theater loses nothing — same invariant as bầu cua. Restart-safe three layers deep like the board games (persisted deadline → lazy resolve on next click → idle sweeper refunds), and `handleExpiredGame` refunds all stakes
- `/masoi` — Ma Sói (Werewolf), the one **social-deduction** game and the only one gated to a **voice channel's built-in text chat**: `execute` refuses unless `interaction.channel.type === ChannelType.GuildVoice` and the caller is currently in that voice room, and only members in that same voice channel can Tham gia (checked against `guild.voiceStates.cache`, the same source streams.ts uses). Private role actions ride on **ephemeral** replies because the bot has no DM channel (DM intent off): one public **🌙 Hành động đêm** button opens a reply only the clicker sees, branched by role. Its own `lobby → (đêm → ngày → vote)* → kết thúc` state machine in `src/commands/masoi.ts` (NOT a board game), reusing only `fetchBoardMessage` from games.ts and the standard persisted-game infra (`loadGame`/`saveGame`/`endGame`, `scheduleDeadline`, idle sweeper). **Roles** (dealt by `assignRoles`, ~1 sói per 4 players, each special ≤1, ≥1 dân): 🐺 Sói (bầy vote chung một con mồi), 🔮 Tiên tri (soi 1 người → biết phe ngay), 🛡️ Bảo vệ (che 1 người khỏi bị cắn), 🧪 Phù thuỷ (1 bình cứu + 1 bình độc, mỗi loại 1 lần cả ván — cứu là blind: hồi người bị cắn đêm đó, chỉ tốn bình khi thật sự có nạn nhân; độc bỏ qua bảo vệ), 🏹 Thợ săn (chết thì bắn theo 1 người — một pha `hunter` gate chèn vào giữa, có thể dây chuyền), 👤 Dân. Night resolves at its **90s** deadline (`resolveNight`: wolf-majority victim, ties random, guard/witch save, poison); day is a **120s** discussion the host cuts short with 🗳️ Bỏ phiếu; vote (**60s**, or early khi mọi người sống đã bỏ phiếu) lynches the sole top-voted (hoà → không ai chết). Win: hết sói → Dân thắng · sói ≥ phần còn lại → Sói thắng. **Coin: zero-sum peer pot like nối từ** — cược **50** 🪙, phe thắng (sống lẫn chết) chia đều pot, không đốt/không mint (`settlePayout`, pot bảo toàn — verified). One board message edited per phase + ephemeral private actions; restart-safe (persisted `deadline` → lazy resolve on next click → idle sweeper refunds all stakes via `handleExpiredGame`). Pure core `assignRoles`/`winnerOf`/`countVotes`/`settlePayout` exported/testable. Min 4, max 20 (Discord select-menu cap)

## AI-bot players (`src/bots.ts`, the 🤖 Thêm bot button)

Every multiplayer minigame lets any player fill empty seats with AI bots on demand: a **🤖 Thêm bot** button on the game's lobby/board adds one bot per click, capped at **`MAX_BOTS` = 3** (`nextBotId` returns the next free `botai-<n>` id, or null → refuse once 3 are seated). All bot-player concerns live in one module — synthetic ids `botai-*` (never a real Discord snowflake, so `isBotId` distinguishes them everywhere a userId flows), three personas (🤖 Bọt/Kẹo/Mực), `mentionOrName(id)` (the ONE render chokepoint: real users → `<@id>`, bots → their bold name — EVERY board/lobby/settlement render must call it, or an unknown-snowflake mention shows as broken literal `<@botai-1>` text), and the faucet GC (`ensureBotLedger`/`sweepBots`).

- **Bot brain — deterministic for the math games, LLM only where language is needed.** bầu cua/đua thú/roulette (pick a symbol) and blackjack (hit/stand/double = basic strategy) are closed-form, so the bot plays a pure heuristic **synchronously and instantly** — no model call, no delay, 100% reliable (an LLM can't beat a fixed rule, and the Claude CLI cold-start overran the button's interaction timeout on the shared-cpu host anyway → it always fell back). Only **nối từ** keeps the LLM: a valid, non-repeating 2-syllable Vietnamese word that chains has no closed-form heuristic. Its bot turn runs in the **background** (a `scheduleDeadline`, never blocking an interaction) via `askBot` with a **30s** timeout for the cold start; a slow/failed reply just makes the bot pass that turn. `decideBot` (the generic wrapper) ALWAYS carries a deterministic fallback, so a bot decision never stalls a game.
- **Coins (the house faucet — deliberately non-zero-sum so humans/hosts win real coins off bots).** One path per economy:
  - **Host-banker** (bầu cua, đua thú, roulette, blackjack): a bot must be a real settlement participant, so `ensureBotLedger` gives it a 0-balance `coins.json` entry and its stake is MINTED straight into the pot/committed (not debited from any wallet). The host wins/loses against it through the unchanged `settleBankerPayout`, and every bot bet passes the same `maxLiability`/solvency gate as a human (a bet the host can't cover is refused). `sweepBots` — called at EVERY settlement/refund/cancel/expire teardown (incl. the blackjack lobby cancel/expire, since bots seat in the lobby there) — deletes all `botai-*` ledger entries, burning residual winnings. Net: mint when a bot loses (→ the host), burn when it wins (host pays, then swept).
  - **Peer-pot** (nối từ): bots are UNFUNDED — never in `coins.json`. The pot (`STAKE × players`) already mints their stake to the human winners and `payOut`'s ghost guard burns any bot share. Nothing to fund or sweep.
- **GC & isolation** (satisfies "every persistent state has GC"): a funded bot ledger entry is owned by its game's teardown (`sweepBots`), the `syncGuild` member-prune **skips** `botai-*` ids (so a bot funded mid-game survives a restart until its game settles), and `coinRanking` (the `/coin bxh` + agent-leaderboard chokepoint) filters them out — a bot never shows on a leaderboard.
- **Replay carries bots**: every settled game's embed shows a **🔄 Ván mới** button (shared `againRow(game, botCount)` from games.ts) whose id encodes the round's bot count — the next round auto-seats that many bots (capped at MAX_BOTS, solvency-permitting). The clicker becomes the new host; the button handler runs BEFORE the game-exists check (the round is already settled). Board/roulette open a fresh board with the bots pre-betting; blackjack/nối từ open a lobby with the bots pre-seated. The slash command always starts empty (0 bots).
- `src/agent.ts` `askBot({ prompt, system, cwd, maxMs })` — the lean one-shot the LLM bots use: `query()` with `config.botModel` (default `claude-haiku-4-5`, env `BOT_MODEL`), no session/resume, no tools/MCP, no streaming, no project settings — fully isolated from the chat lane's `runAgent`. Only nối từ calls it.

## Coin sinks (`/xoso`, `/danhhieu`)

The economy's faucets (checkin, streams) need matching sinks or coins inflate into meaninglessness. Both sinks burn on purpose:

- `/xoso` — lottery: a ticket CLAIMS a number 00–99, one owner per number per round (số đẹp là của hiếm — first come, first served; omit the option for random free numbers). 10 🪙/số (**7 into the jackpot, 3 burned**), max 10 số/user/round. A round opens on its first ticket and draws `DRAW_DELAY_MS` later (1 hour — a rolling countdown from that first ticket, not a wall-clock time) via `startLotteryScheduler` (1-min tick, started unconditionally in `src/index.ts`): one SOLD number is drawn — so any round with tickets is guaranteed a winner, announced by number ("Số trúng hôm nay: 6️⃣8️⃣"), who takes the WHOLE jackpot. After a draw `drawAt` resets to 0, so the next ticket opens a fresh 1-hour round. Ghost numbers (leavers) are excluded from the draw but their jackpot contribution stays; a round with no live tickets rolls the jackpot over silently and reopens on the next ticket. **One jackpot for everyone** — a hundred numbers for the whole system, drawn ONCE per round (`drawRound`, not a per-guild tick: a shared pot must not be paid out once per server). **The result posts back in every channel that sold a ticket** (`lottery.channels`, guildId → channelId, written on each purchase) so the reveal lands where people were actually buying — per server the resolve priority is `/xoso kenh` pin → that room → system/first sendable (`resolveAnnounceChannel(guild, channelId)`); `channels` is cleared on every draw/reset and refilled by the next round's buyers. `/xoso kenh` (ManageGuild) still toggles a manual override channel — mirror of `/worldcup kenh` — for admins who want every result in one fixed channel. Every real draw appends a `LotteryDraw` (`{ n, winnerId, prize, numbers, sold, at }`) to `history` — newest-first, kept as a bounded ring (last `HISTORY_LIMIT`=20, self-GC on write) — which `/xoso lichsu` renders (newest 10) so past results survive the round reset. Store: `data/global/lottery.json` (`{ jackpot, drawAt, channels, tickets: { userId: number[] }, history: LotteryDraw[] }`); draw mutations (history append + reset) are one synchronous block, announce best-effort after. The announce is a slot-machine spin: a message rattles through ~5 random numbers (decelerating), then lands on the drawn number — the winner is paid and the round reset BEFORE the spin (pure theater); the spin is wrapped in its own try so a hiccup mid-roll still reveals the real result.
- `/danhhieu` — purchasable titles, the purest sink: price is 100% burned. Static `TITLES` catalog lives in the command file (id/label/price/blurb — new title = new entry); `data/global/titles.json` holds `{ owned, equipped }` per person, so a bought title shows up in every server they're in. Exported `titleBadge(userId)` renders the equipped label next to the name in `/diemdanh checkin`, and the bulk `titleBadges(userIds)` does the same for `/coin bxh` with a single store read — that display is the entire value proposition.

## Coin drop (`/coindrop`, `src/commands/coindrop.ts`)

Admin-gated engagement faucet — but **zero-sum, not minted**: the dropped coins come straight out of the dropper's own wallet (the same circulation-over-minting principle as the host-as-banker games), so it never inflates the economy and costs the admin (spam-resistant). Whole command is `ManageGuild`-only (`setDefaultMemberPermissions` hides it in the picker + a runtime check as defense-in-depth). Deliberately **not exposed to the AI agent** — an admin coin-mutation faucet must not widen the agent's coin surface; the agent only *explains* it via the auto-built `commandCatalog()`.

- `/coindrop soluong:<int> soluot:<int, default 5, max 20>` — splits `soluong` coins into `soluot` random **lì xì** packets (`splitLixi`, pure/exported: each packet ≥ 1, Σ == total, "double-average" cap for luck; the last packet takes the remainder). Members race a **Nhặt 🧧** button, one grab per user, each pops the next packet and gets a personal ephemeral "nhặt được X". Closes when all packets are grabbed or after `DROP_DURATION_MS` (5 min).
- **Coin flow (conserved):** the dropper is debited `soluong` up front (escrow, re-checked after the reply await); each grab credits the grabber from that escrow; unclaimed packets refund to the dropper at close (ghost-guarded — a dropper who left the server forfeits the refund, never resurrected). The dropper may not grab their own drop.
- **Store & restart safety:** own `drops.json` per guild, keyed by `channelId` (one open drop per channel; a stale expired one is refused-then-swept). Coins settle synchronously (load→mutate→save, no await between) BEFORE any Discord messaging, so a crash mid-render loses nothing and two rapid clicks can't double-grab. `startCoinDropScheduler` (1-min `startTicker`, started unconditionally in `src/index.ts`) closes + refunds expired drops per guild; its startup catch-up run chốt any drop that lapsed while the bot was down. State is transient so it stays out of the `syncGuild` prune — a leaver's grab is just history.

## Bug reports (`/bug`, `src/bugs.ts` + `src/commands/bug.ts`)

Players report the bot's own bugs; the dev reads them in one place. The ledger is **global** (`data/global/bugs.json`) for the same reason the wallet is: a bug belongs to the BOT, not to a room — pooling it means three people in three servers reporting the same thing see each other's report instead of filing it a fourth time, and the dev has one list. Each report records the guild/channel it was spotted in as reproduction context, never as ownership.

- `/bug baocao` opens a **modal** (tiêu đề ≤100 · mô tả ≤1000 · bước tái hiện ≤500, optional) — a modal because a bug description needs a multi-line box, which a slash option can't give. Confirmation is ephemeral and carries the code (`BUG-014`); the report is also `console.log`'d so `bun run logs` surfaces a new bug the moment it lands.
- `/bug list [trangthai]` (đang mở — default | đã sửa | bỏ qua | tất cả) and `/bug xem ma:<số>` are open to **everyone** — duplicate reports are the one thing worth preventing, and that needs a public list. Only **ManageGuild** changes status (🔎 Đang xem / ✅ Đã sửa / 🚫 Bỏ qua / 🆕 Mở lại): the buttons are rendered only for an admin viewer AND re-checked on click, since an old ephemeral message keeps its buttons after a permission is revoked.
- **GC (no lifecycle event ever deletes a report — a reporter who leaves doesn't un-break the bot), so the store self-prunes on every write**, exactly like the lottery history ring: closed reports (đã sửa/bỏ qua) drop after `CLOSED_RETENTION_MS` (30 days, counted from when they were closed), and the ledger is capped at `MAX_REPORTS` (200) — overflow eats the oldest **closed** report first so open work survives. Spam can't push real reports out: `REPORT_COOLDOWN_MS` (60s) per reporter + `MAX_OPEN_PER_USER` (5) open at once, both checked BEFORE any mutation so a refusal doesn't burn an id.
- Pure core (`fileBug`/`setStatus`/`pruneReports`) takes the store + `now` and is covered by `src/bugs.test.ts`, which also `toJSON()`s the modal and the command — a malformed modal otherwise only breaks in the user's face. Deliberately **not exposed to the AI agent** (no `bot_*` tool): the agent would file its own guesses as user reports, and the tool count is already the MCP-timeout constraint.

## World Cup betting (`/worldcup`, seasonal)

Coin betting on World Cup matches — the whole feature (command registration + scheduler) is gated on `FOOTBALL_DATA_TOKEN` (free tier at football-data.org covers competition `WC`); remove the token after the season and it disappears. Engine in `src/football.ts`, UX in `src/commands/worldcup.ts` (`/worldcup list|cuoc|ve|huy|kenh`).

- Fixtures cached globally in `data/worldcup.json`; every future match with known teams is an open line, locked at kickoff. A 1-min `startTicker` (`startFootballScheduler`) refreshes fixtures (1 API call/tick with a 30s timeout, far under the free tier's 10/min) then ticks each guild (`tickGuild`): settle finished matches, then refresh the **live scoreboard**. It refuses to act against an empty cache (a failed first fetch must not void live books).
- **Live scoreboard** (`updateLiveScores` + `liveEmbed`): for every IN_PLAY/PAUSED match a guild has a book on, the tick keeps a single live-score message fresh in the announce channel (`isLive`; `match.score` reads the running score football-data updates during play, "0–0" before the first goal). First live sighting posts it and persists the handle on the book (`MatchBook.live = { channelId, messageId }`); later ticks edit it in place (id unchanged → no store write); the message vanishing (deleted / announce channel moved) reposts. When the whistle blows, settlement **finalizes that same message in place** — edits it into the settlement embed instead of posting a new one — so a match is one message cradle-to-grave (Go Live pattern); a match whose live message never posted (bot was down) still gets a fresh settlement post. Only guilds with a book see a scoreboard — no spamming every WC match to uninterested servers. Live data freshness rides on the free tier (status + score, possibly delayed); the mechanism reflects whatever the API returns each minute.
- One ticket per user per match: `BET_TICKET_FEE` (default 10 🪙, burned) + stake (goes into the match pot). Tickets are immutable; `/worldcup huy` forfeits everything (stake stays in the pot) and frees the slot for a new ticket. Flow: `/worldcup cuoc` → select match → pick button (Hòa only offered in group stage) → stake modal; all state rides in customIds, only `betting.json` persists. Bets are public by design: placing/cancelling a ticket is announced in the channel with a user mention, and `/worldcup list`/`/worldcup ve` show who bet what — only the wizard steps (select/pick) stay ephemeral so others can't click someone else's components.
- Settlement is pari-mutuel (`settleBook`, pure/exported): winners (pick == `score.winner`, i.e. the overall result incl. extra time & pens) split the whole pot pro-rata by stake, floored, remainder burned; nobody right → active tickets get their stakes back; match CANCELLED → stake + fee (recorded per ticket at purchase) refunded; a match missing from the fixtures keeps its book and logs a warning — never auto-void on an API glitch. Payouts skip members who left (ghost guard); leavers' tickets are removed by `removeMemberData`, their stake stays in the pot.
- Shared store `data/global/betting.json` `{ books: { [matchId]: { pot, tickets, rooms? } } }` — ONE pari-mutuel book per match for the whole system (a bigger crowd is strictly a better pool), so **settlement runs once globally** (`settleAll`, not per guild: settling per guild would pay from the first server's pass and leave the rest with a vanished book and no announcement). `rooms` is guildId → `{ channelId, messageId? }`, written when someone bets there: it names every server that played, and carries that server's live-score message so the settlement finalizes it in place. Announcements (settlement + live score) go to the shared `settings.announceChannelId` via `resolveAnnounceChannel` (`/worldcup kenh`, needs ManageGuild, toggles — mirror of `/xoso kenh`); no channel set → falls back to the betting room, then system/first sendable, else stays silent. Books nobody ever bet on close without announcement.

## Wiki (`/wiki`, `src/wiki.ts`)

The bot's self-knowledge lives in **one** place and feeds **two** consumers: a public web page for players and the agent's own reference. `src/wiki.ts` builds a `WikiSection[]` document from the LIVE catalogs — `commandCatalog()`, `CLASSES`, `UNIQUES`, `MOD_POOL`, `AURAS`, `CURSES`, `PASSIVE_NODES`, `ASCENDANCIES`, `BOONS`, `MAP_MODS`, `STAGES`, `ATLAS_NODES`, `QUESTS`, `FLASKS`, `TITLES`, `ENHANCE_TABLE`, the minigame constants — and, where a number comes from a function rather than a constant, by CALLING it (`levelUpCost`, `armourDR`, `evadeChance`, `mapTier`, `enhanceCost`, `salvageYield`, `npcSellPrice`). Add a unique / aura / map mod / command and it appears in both surfaces on the next deploy with no second edit. This is the same anti-drift rule `/help` already follows, applied to everything.

- **The page** — `src/wiki-web.ts` renders the document into one self-contained HTML doc (inline CSS/JS, sidebar TOC + scroll-spy, client-side search, `/` focuses it), served at `GET /wiki` in `src/server.ts`. Fully **static**: no auth, no per-user state, identical for everyone, so it renders once into a module-level cache and is served with an **ETag + `must-revalidate`** (a matching `if-none-match` returns 304). Deliberately not a long `max-age`: the page changes on every deploy, so a reader who visited an hour before a fix would keep being served the broken copy — that is how a shipped font fix once appeared not to have shipped. Aesthetic matches the `/rpg` page (obsidian + engraved gold) so the two read as one product. Wide tables scroll inside their own container — the page body never scrolls sideways.
- **The agent** — `wikiSkillFiles()` renders the SAME document as the `orb-bot` skill: a small always-loaded `SKILL.md` (the tools-only mutation rule, the sender-binding rule, the wiki link, an index) plus one `reference/<section>.md` per top-level section that the agent Reads on demand. `src/index.ts` calls `installGeneratedSkill("orb-bot", wikiSkillFiles())` at ClientReady **before** the guild-sync loop, writing into `template/.claude/skills/orb-bot/` (gitignored — a build artifact); `syncGuild`'s existing `refreshSkills` overlay then carries it into every workspace. The generator is never imported by `guilds.ts` (that would be an evaluation cycle) — `index.ts` composes the two halves.
- **Numbers are published on purpose**: drop rates, affix tier bands + ilvl gates, enhancement break odds, every game's house edge. `src/wiki.test.ts` guards the link between page and engine (enhancement rates match `ENHANCE_TABLE`, every command/unique/aura/gem/region/affix appears, no `undefined`/`NaN` leaks, table rows match header width, `SKILL.md` stays under 8 KB). The percent formatter has its own regression test: an earlier version trimmed trailing zeros with `/0+$/` and silently rendered 100% as "1%" and 90% as "9%" — every round rate on the page was a tenth of the truth and looked entirely plausible.
- Balance constants the wiki prints are `export`ed from their own modules rather than copied here, and `FLOOR_KIND_ODDS` (rpg-maps.ts) exists as a table for exactly this reason — the rate the engine rolls and the rate the wiki prints are one value.
- The link is surfaced in `/help` (top line of the embed) and in the agent's system prompt (`config.wikiUrl`, defined in config.ts so the link's users need no wiki import).

- **Out-levelling penalty + new-ground bonus (anti low-tier farming)** — `rewardMultiplier(level, stage, tier)` in rpg.ts is PoE's XP-penalty shape: an area level derived from `stage.order` + map tier, a safe zone of `3 + floor(level/16)` that widens as you level, then `((lvl+5)/(lvl+5+diff^1.6))^1.5` floored at 0.25. The exponent is 1.6, NOT PoE's 2.5: PoE assumes a 1-100 level scale and ours caps at 50, so 2.5 collapsed almost every out-levelled run straight onto the floor (measured against the journal: even a hero who had climbed to tier 5 took the maximum cut). 1.6 keeps a wide middle band where pushing one or two tiers visibly pays. It scales **gold + ✨ Essence only** — gear is left alone because item level already caps what a shallow map can yield. Crucially the area level comes from what the player CHOOSES (region + tier), never the floor they're standing on: every run starts at floor 1, so a floor-based penalty would tax the opening stretch of every expedition. Penalising only applies when farming BELOW your level; running harder content always pays full. The paired carrot is `NEW_GROUND_BONUS` (+35% gold/Essence on floors deeper than that stage's record) in expeditions.ts, so advancing outearns any farm route and a player who keeps pushing never meets the penalty. The map panel shows the live multiplier per region so it is a visible choice, not a silent tax
- **Progression curves (geometric, PoE-shaped)** — `levelUpCost` is `2.5 × 1.20^level` ✨ Essence, calibrated against MEASURED income (the journal shows ~1,772 ✨ per expedition, ~27.5k/day — an earlier 1.14 guess made the whole climb seven runs). It totals ~114k: level 10 costs ~15, level 49 alone costs ~19k (about ten expeditions for one level). Dying takes Essence too (`deathEssencePenalty`): free below level 8, ramping to `DEATH_XP_PENALTY_MAX` (12%) at cap, charged in expeditions.ts's settle BEFORE the run's loot banks so a full haul can't dodge it. Boss damage also scales with depth (`1.7 + min(1.3, floor×0.004)` in genMonster) — ×1.5 at floor 10 up to ×2.9 deep — while rpg-combat's MAX_HIT_FRAC still forbids a one-shot, so a deep boss reads as "this drains me fast", never as an unavoidable death
- **Affix rolling (PoE's weighted-pool model)** — `ModDef.weight` is a spawn weight and `rollOneMod` draws from a SINGLE flat pool of every eligible `(affix family × tier)` entry, weighted `def.weight × tier.weight`. Picking a family uniformly and then its tier was the earlier shape and it had two faults: adding any affix silently rarefied every existing one (measured: staples lost ~10-18% frequency when spirit/mana were introduced), and a family whose top tiers were still ilvl-locked stayed as common as a fully-unlocked one. Weights are modelled on PoE's distribution — staples high (life 1000, elemental res 800), niche low (chaos res 260, spirit 320). Observed shares track the design within ~1.3 points; the small shortfall on common affixes is expected, since one-mod-per-group means a popular family is more often already taken. 🟠 Huyền Thoại has a genuinely wider canvas — **4p/4s** against everything else's 3p/3s — but its eighth affix is gated on `LEGENDARY_FULL_ILVL` (40), so a shallow legendary rolls 6 and only depth yields the full 8. It is also deliberately scarce (~2-4% of drops). That combination is the long-tail curve the game is tuned for: usable gear is everywhere (Hiếm+Sử Thi ≈ 60% of drops), while perfection recedes — **T1 is the scarcity dial for the whole item chase** (weight 3 against T4's 100, and gated at ilvl 40 so only deep maps roll it): a single mod lands T1 on 1.67% of rolls, so of full 8-affix legendaries 12.6% carry ≥1 T1, 0.73% carry ≥2, 0.024% carry ≥3, 0.0005% carry ≥4. Every rung is a few dozen times harder than the last and none is impossible. **Nothing else may hand out a T1**: a 🌟 jackpot grants the CANVAS (guaranteed Huyền Thoại, full affix count, `JACKPOT_ILVL` depth) and rolls its tiers off the same pool as any drop, and ⭐ Ghép Sao crafts up to `MERGE_BEST_TIER` (T2) only. Both rules exist because the measured alternative was fatal: with jackpots forcing every affix to T1, **55-60% of every Huyền Thoại in play was a pre-perfected jackpot item**, the tier ladder above was decorative, and the player market had nothing worth listing (9 listings in 15 days). All of this is guarded by the `affix RNG integrity` tests (weight proportions, tier curve, ilvl gating, slot restriction, no duplicate group, cap adherence, jackpots never arriving pre-perfected, crafting never reaching T1)
- **Spirit & Mana (the two resource axes, PoE-shaped)** — `spirit`/`mana`/`manaRegen` are StatIds like any other, but they gate rather than damage. The **spirit** affix is slot-restricted (`ModDef.slots` → weapon/body/ring only, mirroring PoE2's sceptre-body-amulet) and every tier is sized to cross an aura threshold, because a spirit roll too small to unlock anything would be a dead mod. **Mana** is priced per swing: `SkillGemDef.manaCost` × each linked support's `manaMult` (`skillManaCost` in rpg-skills.ts — a support that can't apply is never billed). rpg-combat's `act()` gates each swing on the pool: full price → the supported skill, base price → `Fighter.basic` (the bare skill), below that the swing is skipped. Mana is carried across a whole run (`Expedition.mana`, topped up `MANA_FLOOR_RECOVERY` per floor), so support-heavy builds must invest in mana gear or fade to basic swings deep in — measured: 0-2 supports never starve, 4 supports land ~74% full swings
- `src/rpg-boons.ts` — **ân huệ**, the per-run build layer: a catalog of run-scoped buffs (most with a real cost), offered 1-of-3 at every Trạm Dịch and folded onto the hero Fighter each floor by `applyBoons`. Pure. NO boon may touch max life — the expedition rebuilds the hero each floor with `life` = current hp against a frozen `combat.maxLife` that the one-shot cap and flask heal both key off, so moving the ceiling would desync all three (guarded by a test)
- `src/rpg-quests.ts` — **nhiệm vụ hằng ngày**: three finishable daily targets drawn from what a run already reports (floors/elites/bosses/depth/chests), UTC-day keyed to match the telemetry rotation. Pure; the board is credited and paid out ONCE at expedition settle (never per floor, so a lazy resolve or reconcile can't double-pay). Rewards are materials + coins, deliberately never power. Exists because telemetry showed players hit MAX_LEVEL in hours and then left — a cap with nothing finishable behind it
- `src/rpg-telemetry.ts` — the RPG **balance-tuning journal**: an append-only JSONL of every engine event (`RpgEventInput` union — expedition_start/floor_resolved/expedition_end, enhance/salvage/vendor_sell/supply_buy/market_list/market_buy, character_created/level_up/ascendancy_chosen/prestige/passive_alloc/passive_dealloc/passive_respec/atlas_alloc/gem_equip, pvp_invade), one line per event via `logRpgEvent`/`logRpgEvents` (best-effort — a telemetry error never touches game state; emitted only AFTER the synchronous ledger save). Files are date-named `data/guild_<id>/rpg-telemetry-<YYYY-MM-DD>.jsonl` (free daily rotation), season-stamped so they survive a season wipe, and reclaimed only by `startTelemetryScheduler`'s retention prune (`pruneTelemetry`, default 60 days — the GC that bounds the Fly volume). Domain cores stay pure and return richer data (e.g. `CombatResult`'s per-fight dmg-dealt/taken/spike/evade counters feed `floor_resolved`); the imperative shells (expeditions.ts, commands/rpg.ts cores, rpg-pvp.ts) do the emitting. On by default; `RPG_TELEMETRY=0` silences it. Not exposed to the AI agent
- `src/rpg-telemetry-report.ts` — `bun run rpg:stats` (`[--guild <id>] [--since YYYY-MM-DD] [--json]`): reads the journals and prints the balance report — death-rate by (act, tier) + death-floor histogram, drop rates actual-vs-designed (unique/jackpot), enhance up/down/break% vs `ENHANCE_TABLE`, coin faucet/sink flow + inflation, passive pick-rates + never-picked nodes, ascendancy/prestige/max-level funnel, build DPS/EHP percentiles, PvP win-rate. Pure read-only. Run on prod via `fly ssh -C "cd /app && bun run rpg:stats"`
- `template/` — master copy for new server workspaces: `CLAUDE.md` (personality), the room-shaped stores (`streams.json`, `sessions.json`), `data/` knowledge dir
- `data/` — `global/` (the shared world: wallets, heroes, market, ladder) + one folder per server (`data/guild_<guildId>/`); in production this is the Fly volume mount

## Key flows

- Message → `handleMessage` (filter: mention/reply/DM — every server member may use the AI lanes) → prompt = quote context + `[sender]: text` + attachments: when the message is a reply, the quoted message's content (truncated to 500 chars) is prepended; image attachments (png/jpg/gif/webp ≤5MB, max 4 across the message and its quote) are downloaded to `<workspace>/tmp/` and their paths listed in the prompt for the agent's Read tool, deleted after the run → `runAgent` (one-shot query, resume via stored session id, hard 10-min abort so a hung run never blocks the channel queue) → live preview: token deltas (`includePartialMessages`) stream the draft answer into the placeholder on a 1.5s edit tick, tail-cropped past 1500 chars, with the current tool/skill as a `-#` subtext status line (friendly Vietnamese labels via `toolActivity`) → final text split by the shared `chunkForDiscord` (`src/agent.ts`, also used by `/hoi`) into ≤2000-char Discord messages. A subscription-quota rejection (CLI emits a rejected `rate_limit_event`, then a result with `is_error`) throws `AgentLimitError` (src/agent.ts) whose Vietnamese message carries the reset time as a `<t:resetsAt>` Discord timestamp — chat.ts and `/hoi` show it verbatim; every other error keeps the generic "😵 Có lỗi rồi bro" wrap.
- Interaction → look up `commands` Map by name → `execute(interaction)`.

## Conventions

- `bun` always — never npm/node
- One command = one file under `src/commands/`, wired in `src/commands/index.ts`
- No util/helper grab-bags — keep logic inline where it's used; a repeated shape gets extracted into one focused module that owns it outright (`src/scheduler.ts` for timing, `src/games.ts` for betting-board games) — duplication never stays standing
- Bot-facing strings in Vietnamese (xưng "mình", gọi user "bro"); code identifiers in English
- Every `emoji` literal must be a real Unicode emoji (RGI). Discord rejects the WHOLE message with `COMPONENT_INVALID_EMOJI` (400) when a button/select option carries a glyph that merely looks like one, so a single bad catalog entry bricks the entire panel — and only once that item drops. `src/emoji.test.ts` scans the source for `setEmoji("…")` / `emoji: "…"` and asserts `/^\p{RGI_Emoji}$/v`, so new catalogs and buttons are covered with no edit there
- Iteration-first: small, obvious changes; no premature abstraction

## Operations

Production runs on **Fly.io**: app `orb-of-ai`, region `sin`, https://orb-of-ai.fly.dev — a single machine, because a Discord gateway bot on two connections answers everything twice; keep `--ha=false` on deploys and never run a local instance while the Fly machine is up. Real data lives on the Fly volume `orb_data` mounted at `/app/data` (the repo's local `data/` is a stale pre-migration snapshot — never treat it as source of truth). `CLAUDE_CONFIG_DIR=/app/data/.claude` (fly.toml) keeps agent transcripts on the volume so channel sessions survive redeploys. The Dockerfile installs the Claude Code CLI native binary and sets `CLAUDE_PATH=/root/.local/bin/claude` — `agent.ts` exits at startup without a resolvable CLI. Secrets come from `fly secrets` (imported from `.env`, minus `PORT` which fly.toml pins to 8080).

- `bun run dev` — local watch mode (Bun auto-loads `.env`); `fly machine stop` first or the bot answers twice
- `bun run register` — (re)register slash commands after adding/changing one
- `bun run emojis:gen` then `bun run emojis:upload` — one-time per bot application: rasterize the 53 card PNGs (`assets/cards/`, via the dev-only `@resvg/resvg-js`) and upload them as **application emojis** (`bj_*`) for the blackjack render. Idempotent (skips existing; `--force` replaces). Until this runs, blackjack cards fall back to plain text — the bot works either way. Emojis live on Discord (not the Fly volume), so this is per-application, not per-deploy
- `bun run items:gen` (`--force` to redo) — one-time asset step: generate the RPG item art (one PNG per gear base + per unique) into `assets/items/`, served at runtime by the `/rpg` web page (`GET /rpg/asset/item/<key>.png`). Idempotent (skips existing). Shells out to the local `/grok-image` skill (xAI OAuth; `/codex-image` when the Tailnet endpoint is up) — a LOCAL authoring tool, never run in prod. Only legacy jackpots match (top rarity + full affix count + every affix T1 — a shape natural rolling produces with probability ~1e-11), so it is safe and idempotent; a run re-rolls at `JACKPOT_ILVL` because those items *are* jackpots. - `bun run typecheck` — `bunx tsc --noEmit`; `bun test` runs the suite against `.test-data/` (auto-redirected via `NODE_ENV=test`, so a test run can never touch a real ledger)

- `bun run deploy` (= `fly deploy --remote-only --ha=false`) — ship to production; `bun run logs` for logs, `fly ssh console` for a shell
